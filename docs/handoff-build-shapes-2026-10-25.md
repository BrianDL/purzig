## (i) The entry text: before and after

**Before** — `build/purzig.zig`, file-scope `const program_source` (a 45-line
Zig multiline literal), written by `addExecutable` into the build cache with
`b.addWriteFiles()`:

```
    \\// GENERATED by purzig's build helper. Do not edit.
    \\//
    \\// The program. ...
    \\const std = @import("std");
    \\const rt = @import("runtime");
    \\const purs_main = @import("purs_main");
    ...
    \\fn mainNative(init: rt.ProcessInit) !void {
    \\    rt.init(init.io, init.arena.allocator());
    \\    _ = try rt.runEffect(try purs_main.@"ps.main"());
    \\}
    ...
    \\fn mainFreestanding() void {
    \\    @trap();
    \\}
    \\
    \\pub const main = if (rt.freestanding) mainFreestanding else mainNative;
    ...
    \\pub fn runWithAllocator(allocator: std.mem.Allocator) rt.Error!void {
    \\    rt.initAlloc(allocator);
    \\    _ = try rt.runEffect(try purs_main.@"ps.main"());
    \\}
```

**After** — `entry/entry.zig`, the same 45 lines as a real file, unescaped:

```zig
// GENERATED by purzig's build helper. Do not edit.
//
// The program. This file is the executable's root, not a module:
// every output-zig/<Module>.zig is a module, and none of them knows
// which one exports `main`. It is written into the build cache, so
// nothing lands in the project's output-zig/ but modules.
//
// `purs_main` is the module that exports `main` (Options.main_module),
// bound by the build helper under a fixed import name.

const std = @import("std");
const rt = @import("runtime");
const purs_main = @import("purs_main");

// ... comments unchanged ...

fn mainNative(init: rt.ProcessInit) !void {
    rt.init(init.io, init.arena.allocator());
    _ = try rt.runEffect(try purs_main.@"ps.main"());
}

// ... comments unchanged ...

fn mainFreestanding() void {
    @trap();
}

pub const main = if (rt.freestanding) mainFreestanding else mainNative;

// ... comment unchanged ...
pub fn runWithAllocator(allocator: std.mem.Allocator) rt.Error!void {
    rt.initAlloc(allocator);
    _ = try rt.runEffect(try purs_main.@"ps.main"());
}
```

**Confirmation that the text did not change.** The literal was extracted
mechanically from `git show HEAD:build/purzig.zig` (strip the `    \\` prefix of
each line of the `program_source` literal, join with `\n`) and compared with
`entry/entry.zig`:

```
$ diff <extracted literal> entry/entry.zig
45c45
< }
\ No newline at end of file
---
> }
```

That is the whole difference: **a file ends with a newline and a Zig multiline
literal does not.** No line differs, so **the import line does not differ
either** — the before text already declared
`const purs_main = @import("purs_main");` and both call sites were already
`purs_main.@"ps.main"()` (they were rewired in the previous change, issue #7).
Nothing was added, removed or reworded, and nothing is substituted at build
time: the shipped file *is* the program.

Deliberately kept verbatim, and therefore still present:

- the `// GENERATED by purzig's build helper. Do not edit.` header (accurate in
  effect — the helper copies these bytes into the cache; a future change may
  reword it, this one may not, because this move is byte-for-byte);
- `fn mainFreestanding() void { @trap(); }`;
- `pub const main = if (rt.freestanding) mainFreestanding else mainNative;`.

`build/purzig.zig` now contains **no** driver text at all — in particular no
`rt.init` / `rt.initAlloc` anywhere, including its comments, so
`grep -n 'rt.init' build/purzig.zig` is empty (checked: no match).

### The one spelling difference from the issue

The issue says "replace the literal with `@embedFile("entry/entry.zig")`".
Zig resolves `@embedFile` **relative to the directory of the file that contains
the call**, not relative to the build root, and the call is in `build/`
(`@import("build/purzig.zig")` from `build.zig` makes it the same module, but
the base directory is still `build/`). The shipping spelling is therefore:

```zig
const entry_source = @embedFile("../entry/entry.zig");
```

If the toolchain in use resolves it against the build root instead, the build
fails with `unable to load '../entry/entry.zig'` and the fix is to drop the
`../` — one token, nothing else depends on it. This is the only place the
change departs from the issue text.

### The wiring in `addExecutable`, unchanged apart from the source of the bytes

```zig
const write_program = b.addWriteFiles();
const program = write_program.add("purzig_entry.zig", entry_source);
```

The file name in the cache stays `purzig_entry.zig`, the `purs_main` import
binding stays, and `exe.step.dependOn(&codegen.step)` stays. The program shape
is not touched, so the downstream parity gate's assumption holds (see the end).

## (ii) `addLibrary`

Exact signature, in `build/purzig.zig`:

```zig
pub fn addLibrary(b: *std.Build, opts: Options) LibraryArtifacts

pub const LibraryArtifacts = struct {
    codegen: *std.Build.Step.Run,   // the `spago build` invocation
    runtime: *std.Build.Module,     // the purzig runtime module
    module:  *std.Build.Module,     // output-zig/<opts.main_module>.zig, `runtime` bound
};
```

What each returned artifact is for:

| field | what it is | what a caller does with it |
|---|---|---|
| `codegen` | the same `*std.Build.Step.Run` `addExecutable` returns: the shim + package-set copy + `spago build` in the project directory | order its own artifact after it — `my_artifact.step.dependOn(&lib.codegen.step)` — because `output-zig/*.zig` does not exist on a clean checkout, and (in-tree) hook the backend bundle build into it |
| `runtime` | the `runtime/root.zig` module built for `opts.target` / `opts.optimize`, the one already bound as `runtime` on `module` | bind the *same* module, not a second copy, on a root that also wants `rt.ProcessInit` / `rt.runEffect` |
| `module` | `b.createModule(.{ .root_source_file = <project>/output-zig/<opts.main_module>.zig })` with `runtime` added as an import | `root.addImport("purs_main", lib.module)` and call `purs_main.@"ps.main"()`, or import it under any other name |

Guarantees, matching the issue:

- **no entry file**: `addLibrary` never calls `b.addWriteFiles()`, so a
  library-only build leaves `output-zig/` holding modules + `manifest.json` and
  no `purzig_entry.zig`;
- **no program decision**: no `b.addExecutable`, no `b.installArtifact`;
- **`opts.main_module` keeps its default `"Main"`** and is used by
  `addLibrary` only to pick which generated module becomes `module`;
- **`output-zig/manifest.json` is still not parsed** — the module name is a
  constant from `opts`, exactly as in `addExecutable`;
- `opts.name` is ignored by this shape (a library installs nothing);
- `b.addExecutable` and `Artifacts { exe, codegen, runtime }` are unchanged, so
  every existing downstream caller and the parity gate compile against the same
  API they did before.

The shared half lives in a private helper rather than being copy-pasted:

```zig
const Codegen = struct {
    codegen: *std.Build.Step.Run,
    runtime: *std.Build.Module,
    main: *std.Build.Module,
};

fn addCodegen(b: *std.Build, opts: Options) Codegen
```

`addExecutable` = `addCodegen` + entry + executable; `addLibrary` = `addCodegen`
+ hand the module out. The body of `addCodegen` is the old `addExecutable`
sections 1 and 2 and the module-creation block, moved, not rewritten: the shim
still uses `absFromRoot(pb, "compiler/dist/bundle.js")` and
`absFromRoot(b, ".zig-cache/purzig-bin")`, the package-set copy still tolerates
a missing set, `codegen` is still `spago build` with `setCwd(project)`,
`has_side_effects = true` and `addPathDir(bin_dir)`.

## (iii) How the library fixture roots itself

`example/library/libmain.zig` — a consumer's root, not purzig's entry:

```zig
const rt = @import("runtime");
const purs_main = @import("purs_main");

pub fn main(init: rt.ProcessInit) !void {
    rt.init(init.io, init.arena.allocator());
    _ = try rt.runEffect(try purs_main.@"ps.main"());
}
```

- **module name**: `purs_main`, and it is a *binding the build makes*, not a
  file next door — `build.zig` does `lib_root.addImport("purs_main", lib.module)`
  where `lib.module` is `addLibrary`'s return value. `runtime` is bound the same
  way from `lib.runtime`. Nothing else is wired.
- **call**: `try purs_main.@"ps.main"()` builds the `Effect` thunk, and
  `rt.runEffect(...)` forces it — the same two steps the entry performs.
- **assertion**: `build.zig` builds the root with `b.addExecutable(.{ .name =
  "library-probe", .root_module = lib_root })` (not installed),
  `lib_probe.step.dependOn(&lib.codegen.step)`, then
  `const check_library = b.addRunArtifact(lib_probe);
  check_library.expectStdOutEqual("Hello, Zig\n")`, exposed as
  `zig build test-library` and added to `zig build test`.

`expected_output` is the same constant `test-e2e` uses, so the two shapes are
asserted against the same string. The program prints it because `Main.purs` is
unchanged: `target "Zig"` → `greet` → `"Hello, Zig"`.

`lib.codegen.step` also gets two in-repo dependencies, both deliberate:

- `dependOn(&build_compiler.step)` — the bundle is built from source here, so
  codegen must never run against a stale `compiler/dist/bundle.js`;
- `dependOn(&app.codegen.step)` — both codegen steps run `spago build` in the
  *same* directory (`example/`), and the build runner would otherwise start the
  two in parallel. This only orders steps; it does not build the example
  executable.

## (v) The one command

Run from the repository root:

```
zig build test-e2e && zig build test-library && zig build test-runtime \
  && zig build -Dtarget=wasm32-freestanding -Doptimize=ReleaseSmall \
  && head -c 4 zig-out/bin/example.wasm | od -An -c
```

Expected, in order: `test-e2e` exits 0 having asserted stdout is exactly
`Hello, Zig\n`; `test-library` exits 0 having asserted the *library* probe
prints the same; `test-runtime` exits 0; the freestanding build exits 0; the
last line is

```
   \0   a   s   m
```

Notes:

- `zig build test-e2e` depends on `zig build compiler` (`spago bundle`), so the
  bundle is regenerated from `compiler/src` first. `test-library` depends on the
  same step, for the same reason.
- Zig has named installed wasm artifacts `example.wasm` in some versions and
  `example` in others. If `zig-out/bin/example.wasm` is absent, `ls zig-out/bin/`
  and `head -c 4` the file that is there; the criterion is about the four bytes.
- Do **not** add `-Dtarget=wasm32-freestanding` to `test-library`: it runs its
  artifact, and the fixture root has no freestanding arm (a library does not
  decide how a host starts).
- A plain `zig build` builds and installs only the program; `test-library`
  compiles into the cache and installs nothing, so `zig-out/bin/` gains no
  `library-probe`.
- Criterion 6 by hand: `zig build codegen`, then `ls example/output-zig` should
  show `*.zig` + `manifest.json` and no `purzig_entry.zig`.

## The downstream parity gate

`sophos/purzig-template` (a different repository, not visible from this
environment) builds against this branch and asserts the program's **exact
stdout**. That is why the driver text was moved **verbatim**: the entry file is

### One follow-up outside this diff: `build.zig.zon` `.paths`

`entry/` is a *shipped* file, and `build.zig.zon` carries an allowlist:

```zig
    .paths = .{
        "build.zig",
        "build.zig.zon",
        "build",
        "runtime",
        "compiler/dist",
        "packages",
        "packages.json",
        "LICENSE",
        "README.md",
    },
```

`"entry"` is not in it. A consumer that pulls purzig **by URL/tarball** gets a
filtered tree, so `@embedFile` would not find `entry/entry.zig` and the build
script would fail to compile. A consumer that depends on purzig by **path**
(which is how a branch is normally tested, and how `purzig-template` would be
pointed at this branch) uses the checkout directly and is unaffected.

This file is out of scope for this change — the issue forbids touching
`build.zig.zon`, and the acceptance criterion for the diff excludes it — so the
one-line fix is recorded here instead:

```diff
         "compiler/dist",
+        "entry",
         "packages",
```

It must land before the next tag, or the tarball is missing the program. Also
note that adding it changes the package hash, which is why it belongs to the
release step rather than to this PR.
