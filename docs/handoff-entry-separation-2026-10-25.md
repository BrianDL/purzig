# Handoff: the entry point moves out of the generated modules (issue #7)

**Date:** 2026-10-25
**Scope:** `sophos/purzig` issue #7 — the emitter emits **modules only**; the
program becomes `output-zig/purzig_entry.zig`, the output gets described by
`output-zig/manifest.json`, and `build/purzig.zig` roots the executable at the
entry file.
**Status:** change written, **not executed**. No `zig`, `purs`, `spago` or
`node` was available in this environment and none was installed, no build or
container was run. Nothing below is a measured result. Criteria 2–5 are
**UNVERIFIED**.

## The entry point: before and after

The template lived in `Zig.Emit.emitModule` as `entry`, gated on
`isEntry = name == "Main"`, and was appended to that module's output. The text
below is what it rendered to.

### Before — the tail of `output-zig/Main.zig`

```zig
// GENERATED by purs-backend-zig from Main. Do not edit.

const std = @import("std");
const rt = @import("runtime");

const @"mod.Effect.Console" = @import("Effect.Console.zig");
… (one import per surviving import, then the module's own decls) …

pub fn @"ps.main"() rt.Error!rt.Value {
    …
}

                                <- the moved block starts here (one blank line)
// The entry point is chosen at comptime, so this file is identical for
// every target. Zig analyses what is REFERENCED, not what runs, so the
// native half below must not be reachable from a freestanding build:
// that target has no process, no `Io`, no console and no panic printer.
//
// Native: zig 0.16 hands `main` an `Io` and a process-lifetime arena,
// both wrapped in the type its start code passes in. That type is spelled
// `rt.ProcessInit` so it does not appear in generated sources, and so a
// freestanding target -- where it does not exist -- has one place to say
// so.
fn mainNative(init: rt.ProcessInit) !void {
    rt.init(init.io, init.arena.allocator());
    _ = try rt.runEffect(try @"ps.main"());
}

// Freestanding: no process, so no `Io`, no arena and no console. Nothing
// can run until a host binds memory through `rt.initAlloc`, so the start
// function traps instead of pretending the program ran.
fn mainFreestanding() void {
    @trap();
}

pub const main = if (rt.freestanding) mainFreestanding else mainNative;

// The freestanding seam: a host calls this once it owns the memory.
// Deliberately unreferenced -- zig analyses only what is referenced, and
// every console primitive this program uses is native-only.
pub fn runWithAllocator(allocator: std.mem.Allocator) rt.Error!void {
    rt.initAlloc(allocator);
    _ = try rt.runEffect(try @"ps.main"());
}
```

`output-zig/Main.zig` now ends at `@"ps.main"`'s closing brace. It keeps
`const rt = @import("runtime");`, its `ffi` import when it has foreign imports,
and its module imports; it loses the `std` import, which nothing else in a
generated module referenced.

### After — `output-zig/purzig_entry.zig` (the whole file)

```zig
// GENERATED by purs-backend-zig. Do not edit.
//
// The program. This file is the executable's root, not a module:
// every output-zig/<Module>.zig is a module, and none of them knows
// which one exports `main`.

const std = @import("std");
const rt = @import("runtime");
const @"mod.Main" = @import("Main.zig");

// The entry point is chosen at comptime, so this file is identical for
// every target. Zig analyses what is REFERENCED, not what runs, so the
// native half below must not be reachable from a freestanding build:
// that target has no process, no `Io`, no console and no panic printer.
//
// Native: zig 0.16 hands `main` an `Io` and a process-lifetime arena,
// both wrapped in the type its start code passes in. That type is spelled
// `rt.ProcessInit` so it does not appear in generated sources, and so a
// freestanding target -- where it does not exist -- has one place to say
// so.
fn mainNative(init: rt.ProcessInit) !void {
    rt.init(init.io, init.arena.allocator());
    _ = try rt.runEffect(try @"mod.Main".@"ps.main"());
}

// Freestanding: no process, so no `Io`, no arena and no console. Nothing
// can run until a host binds memory through `rt.initAlloc`, so the start
// function traps instead of pretending the program ran.
fn mainFreestanding() void {
    @trap();
}

pub const main = if (rt.freestanding) mainFreestanding else mainNative;

// The freestanding seam: a host calls this once it owns the memory.
// Deliberately unreferenced -- zig analyses only what is referenced, and
// every console primitive this program uses is native-only.
pub fn runWithAllocator(allocator: std.mem.Allocator) rt.Error!void {
    rt.initAlloc(allocator);
    _ = try rt.runEffect(try @"mod.Main".@"ps.main"());
}
```

### The import line added, and the only two other edits

```zig
const @"mod.Main" = @import("Main.zig");
```

This is written by `Zig.Emit.importLine`, the same function that writes every
module-to-module import, so the spelling matches generated modules exactly
(`Ident.moduleRef name` is `@"mod.<Module>"`; dots are legal in filenames, so the
file is `Main.zig`).

The only textual changes inside the moved block, both forced by the move:

| before | after |
|---|---|
| `const std = @import("std");` in `Main.zig`'s header | same line, in `purzig_entry.zig`'s header |
| `_ = try rt.runEffect(try @"ps.main"());` in `mainNative` | `_ = try rt.runEffect(try @"mod.Main".@"ps.main"());` |
| `_ = try rt.runEffect(try @"ps.main"());` in `runWithAllocator` | `_ = try rt.runEffect(try @"mod.Main".@"ps.main"());` |

Nothing else moved or changed: the same `fn mainNative(init: rt.ProcessInit)
!void` signature, the same `rt.init(init.io, init.arena.allocator())`, the same
two `try`s, the same `pub const main = if (rt.freestanding) …` comptime branch,
the same `fn mainFreestanding() void { @trap(); }`, the same
`pub fn runWithAllocator(allocator: std.mem.Allocator) rt.Error!void`, the same
comments. **Same stdout, same exit status, same artifacts** — which is what
`purzig-template`'s `test-e2e` measures. The freestanding trap workaround from
issue #3 is untouched: `mainFreestanding` still exists, still `@trap()`s, and is
still what a freestanding target selects.

## Manifest schema

`output-zig/manifest.json`, written once after every module:

```json
{
  "main_module": "Main" | null,
  "entry_file": "purzig_entry.zig" | null,
  "modules": [
    { "name": "<ModuleName>", "file": "<ModuleName>.zig", "ffi": "<ModuleName>.ffi.zig" | null }
  ]
}
```

Rules, as implemented in `Main.purs`:

- `modules` has one row per **generated module**, in emission (dependency)
  order. Rows come from the decoded CoreFn modules of this run
  (`fromFoldable (sortModules mods)`), and a row is kept only if
  `output-zig/<file>` exists — a module that failed to emit is absent, so the
  manifest never promises a file that is not there.
- `ffi` is `"<Module>.ffi.zig"` exactly when that file exists in `output-zig/`,
  `null` otherwise. It is answered by the filesystem rather than by the
  module's foreign set precisely because the manifest promises files: a module
  that declared foreign imports but shipped no `.zig` beside them gets no ffi
  file, and must not claim one. (Consequence worth knowing: a stale
  `.ffi.zig` left behind by an earlier run in the same directory would still be
  reported, as it would still be on disk and still importable. `zig build
  clean-purs` removes the whole directory.)
- `main_module` is the emitted row whose name is `Zig.Emit.mainModule`
  (`"Main"`); `entry_file` is `Zig.Emit.entryFile` when that row exists. With no
  such module both are `null` and **no entry file is written**, which is also
  what leaves `addExecutable` with a missing root instead of a root that calls a
  decl nobody wrote.
- Extra keys are allowed by the issue and none are emitted: the two constants
  plus the module list are everything a consumer needs, and every extra key is a
  compatibility promise.
- `purzig_entry.zig` is **not** listed in `modules` — it is the program, not a
  module, and it has no `ffi`.

### A real example, constructed by hand — UNEXECUTED

Built from this repository's own fixture (`example/src/{Main,Scratch}.purs` plus
the vendored packages) by running `describe` and `renderManifest` in the head:

```
emitted =
  [ { name: "Data.Semigroup",  file: "Data.Semigroup.zig",  ffi: Just "Data.Semigroup.ffi.zig" }   -- packages/purescript-prelude/src/Data/Semigroup.zig is copied
  , { name: "Effect.Console",  file: "Effect.Console.zig",  ffi: Just "Effect.Console.ffi.zig" }
  , …
  , { name: "Scratch",         file: "Scratch.zig",         ffi: Nothing }                          -- no foreign imports
  , { name: "Main",            file: "Main.zig",            ffi: Nothing }                          -- `log` is Effect.Console's foreign, not Main's
  ]

entry = Just { name: "Main", file: "Main.zig", ffi: Nothing }
```

`renderManifest emitted entry` produces:

```json
{
  "main_module": "Main",
  "entry_file": "purzig_entry.zig",
  "modules": [
    { "name": "Data.Semigroup", "file": "Data.Semigroup.zig", "ffi": "Data.Semigroup.ffi.zig" },
    { "name": "Effect.Console", "file": "Effect.Console.zig", "ffi": "Effect.Console.ffi.zig" },
    { "name": "Scratch", "file": "Scratch.zig", "ffi": null },
    { "name": "Main", "file": "Main.zig", "ffi": null }
  ]
}
```

(The real file lists all ~89 modules in dependency order; the `…` and the two
elisions above are this document's, not the emitter's. This example is a
construction, not a captured run — nothing was executed.)

With no module exporting `main` the same code writes:

```json
{
  "main_module": null,
  "entry_file": null,
  "modules": [
    { "name": "Scratch", "file": "Scratch.zig", "ffi": null }
  ]
}
```

Empty module list renders as `"modules": [\n  ]`, which is valid JSON (an empty
array).

### Criterion 1's greps are stale — read this before judging it

The issue text was written against a state of `master` that predates the
freestanding work, and criterion 1 quotes both an old spelling and an old shape:

1. `grep -rn 'process.Init' compiler/src` finds **nothing** on `master`
   (`0d94a61`), and still nothing after this change. Since issue #3 the driver
   spells the parameter type `rt.ProcessInit`, precisely so `std.process` never
   appears in generated sources — and the issue's "Not included" forbids
   removing that workaround. The nearest real grep finds the template **once**
   (two lines, both inside `Zig.Emit.entryBody`, which is the single place the
   driver is spelled):

   ```
   $ grep -rn 'ProcessInit' compiler/src
   compiler/src/Zig/Emit.purs:216:  , "// `rt.ProcessInit` so it does not appear in generated sources, and so a"
   compiler/src/Zig/Emit.purs:219:  , "fn mainNative(init: rt.ProcessInit) !void {"
   ```

2. `grep -rn 'pub fn main' output-zig/purzig_entry.zig` will find **nothing**
   either, on `master` or after this change: the entry declares
   `fn mainNative(init: rt.ProcessInit) !void` and
   `pub const main = if (rt.freestanding) …`, the comptime form criterion 1
   itself allows in its parenthesis. `grep -rn 'pub fn main' output-zig/Main.zig`
   finding nothing is the half that matters and holds for a different reason:
   `Main.zig` contains no driver at all now.

   ```
   grep -rn 'mainNative\|pub const main' output-zig/purzig_entry.zig   # the entry
   grep -rn 'mainNative\|pub const main\|std\.' output-zig/Main.zig    # nothing
   ```

## Static review only — where to look if the build fails

Nothing was compiled, so these are the assumptions a first run will check, in
order of likelihood:

1. `Main.purs`'s `describe` reads `m.name` off the CoreFn `Module` (the same
   record whose `.path` the file already used) and `unwrap`s it. If the pinned
   optimizer spells that field differently, `purs` fails there with "unknown
   field" and the fix is the field name.
2. `Data.Array` provides `find`, `fromFoldable` and `mapWithIndex` in the pinned
   `arrays` version (`fromFoldable` and `find` were checked against
   `packages/purescript-arrays/src/Data/Array.purs`, which is vendored for the
   fixture; the compiler resolves the registry version).
3. `build/purzig.zig` calls `project.path(b, "output-zig/purzig_entry.zig")` with
   a literal where it used `b.fmt(...)` — same `LazyPath` API, no format string.
4. `Zig.Emit.entryBody` is a plain array of lines; the only non-literal element
   is `entryMain moduleName`, which is `Ident.moduleRef` (already used for every
   module import) concatenated with `Ident.topLevel "main"` (already used for
   every top-level binding).

## Not done, on purpose

- `build/purzig.zig` does **not** read `manifest.json`. The entry filename is a
  constant string; parsing the manifest would make every consumer's build depend
  on its shape for one value. `opts.main_module` is therefore unused inside
  `addExecutable` — it is kept as documented public API (it still names the
  module that exports `main`, and `build.zig` still passes `"Main"`), not as a
  path.
- `compiler/dist/bundle.js` was **not** regenerated (and
  `compiler/dist/bundle.js` is untouched in the diff). `zig build` regenerates it
  through `zig build compiler`, because the codegen step depends on it; commit it
  if the PR needs it. **No build was run, so the committed bundle is still the
  pre-change one** — anyone testing the Zig side without `zig build`'s compiler
  dependency, or anyone running the published bundle, sees the old emitter until
  it is rebuilt.
- `addLibrary`, a `-Dshape=` option, the wasm host ABI, `runtime/apply.zig`,
  `build.zig`, `build.zig.zon`, `packages.json`, `spago.yaml`: untouched.
- `example/src/*.purs` untouched: the fixture must keep printing exactly
  `Hello, Zig`.
- The entry is written for the module named `Zig.Emit.mainModule` (`"Main"`),
  which is exactly the condition `emitModule` used before (`isEntry = name ==
  "Main"`). A project whose `main` module is not called `Main` cannot build
  today either — the old emitter would still have put the driver in `Main.zig`
  while `addExecutable` rooted the executable at `output-zig/<main_module>.zig`
  — so nothing regresses here, and threading `opts.main_module` through to the
  emitter is left to whichever issue actually needs it.
- The emitter is the only place the driver text exists: `Zig.Emit.entryBody`.
  Nothing in `Main.purs`, `build/purzig.zig` or the runtime repeats it.
